## 3. 六个已实测的断裂点

数据都存在，但**没有一块驱动下一块**。

| # | 断裂 | 实测证据 |
|---|---|---|
| 1 | 选股 → 分析 | 近 5 次选股 21 只候选，仅 1 只有分析记录 |
| 2 | 持仓 → 资讯 | 持仓 `sz002567` 在资讯池中无任何条目 |
| 3 | K线 → 资讯 | 13 只有 K线，仅 6 只有资讯；`sh600519`（茅台）也没有 |
| 4 | 建议 → 校准 | 19 条已验证，**方向性样本仅 1 条**，校准门槛为 10 —— 永不可达 |
| 5 | 全市场 → 分析 | 横截面 5565 只，实际分析过 11 只；中间无桥 |
| 6 | 观测缺口 → 补数据 | 数据观测页报告 6 个缺口，无任何机制或流程去补 |

**唯一的正向例外**：持仓 `sz002567` 的分析/建议/档案/K线齐全 ——
因为它是**手动分析过**的。这反过来说明：流程能走通，但没有任何东西自动驱动它。

断裂点 4 尤其值得注意：它不是"数据不够多"，而是**闭环设计不成立** ——
校准要求 10 条方向性样本，而系统产出的建议以 `watch` 为主，
按当前设计**永远无法达到门槛**。这类问题是任何后台任务都修不好的。

## 6. 目标架构：四层单向流水线

现状是"一堆数据仓库"，目标是一条**有方向的**流水线。

```
┌─ L1 采集 ──────────────────────────────────────────┐
│  data_provider（多源降级）                          │
│  → 落库前统一身份 canonical_id                      │
└────────────────────┬───────────────────────────────┘
                     ↓
┌─ L2 事实 ──────────────────────────────────────────┐
│  market_snapshot   全市场横截面（每日一份）          │
│  stock_daily       时序                              │
│  intelligence_items 资讯                            │
│  原则：只存事实，不存判断；一份事实只存一处          │
└────────────────────┬───────────────────────────────┘
                     ↓  筛选 / 触发
┌─ L3 判断 ──────────────────────────────────────────┐
│  analysis_history → decision_signals                │
│  读 L2，不重复抓取                                   │
└────────────────────┬───────────────────────────────┘
                     ↓  到期
┌─ L4 反馈 ──────────────────────────────────────────┐
│  decision_signal_outcomes → 命中率 → 校准            │
│  回流影响 L3 的下一次判断                            │
└─────────────────────────────────────────────────────┘
```

**四条架构原则：**

1. **单向**：只有 L1→L2→L3→L4，不回环。反馈走 L4→L3 的显式校准通道，不走隐秘耦合。
2. **一份事实只存一处**：L2 是唯一事实来源，L3/L4 只存判断与结果，不复制事实。
3. **读本地优先**：L3 消费 L2 时先查库，抓取只是补齐。这样数据源故障不会瘫痪判断。
4. **身份在入口统一**：`canonical_id` 在写入时确定，不靠事后回填。

## 7. 改造路线：按依赖顺序，每步可独立验证

按"能独立交付、能独立回滚、按依赖排序"排列。**不做大爆炸式重构。**

### 第一步：读本地优先（收益最大，风险最低）

给问股工具接上 L2。不新建任何表。

- 新增 `get_company_profile`（读 `company_profile`）
- 新增 `get_market_context`（读 `market_snapshot`，回答"这只票在全市场什么位置"）
- 改 `get_stock_info`：**先查库，库空或过期再抓**

**验收**：断开外网，问股仍能回答该股的行业、估值、全市场分位。

### 第二步：闭环修正（让 L4 真正成立）

断裂点 4 是设计缺陷，必须改设计而不是加数据。

- 校准门槛按**实际可获得的样本量**设定，或改为分档置信（样本 1-5 低置信、6-20 中、>20 高）
- 更根本的是 L3 的产出结构：如果建议以 `watch` 为主，说明**判断没有给出方向**，
  那么要么调整提示词让它给出方向，要么承认"不给方向"也是产出并据此设计反馈

**验收**：连续运行后，校准确实产生了对下一次判断的影响（可观测的差异）。

### 第三步：L2 → L3 的桥（需要确认成本）

- 选股候选自动进入分析（21 → 有分析的比例应显著上升）
- 持仓 + 自选定期分析

**这一步会产生 LLM 调用成本，必须先确认频率与预算。**

### 第四步：存储层收敛（纯减法）

- 合并 `company_metrics` → `fundamental_snapshot`（消除第 4 节的重复）
- `storage.py`（4,500 行 / 37 模型）按域拆分：
  `storage/market.py`、`storage/intelligence.py`、`storage/decision.py`、
  `storage/portfolio.py`、`storage/system.py`
- 一次性脚本（migrate / build_company_profile）删除，只留验收脚本
- 未启用功能的空表：**保留表结构、隐藏入口**（删表会拖出上游依赖，收益不抵风险）

### 第五步：`src/services/` 分层（最后做，风险最高）

88 个文件、57K 行，且被所有层依赖。**必须最后做**，且**只做移动不做改写**：

```
src/services/market/        行情、快照、公司档案
src/services/intelligence/  资讯
src/services/decision/      分析、建议、反馈
src/services/portfolio/     持仓
src/services/screening/     已有，保持
src/platform/               配置、调度、诊断、运行时（现混在 services 里）
```

`system_config_service.py`（5,563 行）单独拆。

## 8. 明确不做的事

- **不引入消息队列 / 事件总线**：当前规模（单机 SQLite、日级数据）用不上，
  引入只会增加运维面。L4→L3 的校准通道用显式函数调用即可。
- **不做全市场完整档案**：5565 只 × 完整财务/概念 ≈ 50 MB/天，而真正被读的只有个位数。
  已按此原则只存数值横截面。
- **不删上游空表**：告警/回测等 6 张空表属于未启用功能，
  删表会牵扯上游代码与迁移，**隐藏入口即可**。
- **不重写 `data_provider/`**：多源降级是这个项目最扎实的部分。

## 9. 度量：改造是否真的有效

架构改造容易变成"感觉更整洁了"。用这几个可测指标判断：

| 指标 | 现状 | 目标 |
|---|---|---|
| 问股工具中读本地库的比例 | 1 / 19 | 主体工具读本地 |
| 断裂点数量（本文第 3 节） | 6 | ≤ 2 |
| 空表数量 | 13 / 35 | 不减（改为隐藏入口） |
| 同一事实的存储处数 | 2（估值） | 1 |
| `storage.py` 行数 | 4,500 | 按域拆分后单文件 < 1,000 |
| 最大单文件行数 | 5,563 | < 2,000 |
| 校准可用样本数 | 1（门槛 10） | 门槛可达且实际生效 |

# P0：独立抓取循环

## 一、问题（有据可查）

资讯只在**跑分析时**才被顺带拉取。

```
拉取触发点：
  POST /intelligence/sources/{id}/fetch      手动
  POST /intelligence/sources/fetch-enabled   手动
  pipeline.py:3030                           个股分析时顺带  ← 自动
  market_analyzer.py:2080                    大盘复盘时顺带  ← 自动
```

`NEWS_INTEL_AUTO_FETCH_ENABLED` 虽然叫"自动拉取"，但**它只是允许"分析时顺手拉"**，不是一个独立的抓取节奏。

**后果**：
- 不跑分析 → 资讯不更新。打开资讯页看到的是旧内容。
- 抓取频率 = 分析频率。分析可能一天一次，也可能一小时十次，**与资讯源的更新速度毫无关系**（最快的源 1 分钟一条）。
- 20 分钟的进程内冷却失去意义：一天跑一次分析时它永远不生效。

**已排除的错误方案**：`SCHEDULE_ENABLED=true` 不能解决。`runtime_scheduler.py` 是 subprocess 跑**完整分析**（`_run_analysis_once` → `analyze_stock`），里面没有任何独立抓取逻辑。开它只会把抓取频率绑到调度频率（默认每日一次）。

---

## 二、目标行为

**抓取节奏由资讯源决定，与分析和调度无关。**

```
现在:  分析 ──顺带──> 抓取          （抓取频率 ⊥ 资讯更新速度）
目标:  循环 ──定时──> 抓取 ──独立于── 分析
                      ↑
              冷却(20min) 是真正的频率控制
```

---

## 三、设计

### 3.1 分层：tick 与 cadence 分开

**这是整个设计的核心，也是它能复用现成机制的原因。**

```
循环 tick      每 5 分钟醒一次（很轻，只做一次判断）
     ↓
refresh_auto_sources()
     ↓
已有的 20 分钟冷却  ← 真正决定"这次抓不抓"
     ↓
fetch_enabled_sources()
```

- **tick 只负责"定期来敲一次门"** —— 保证冷却会被周期性评估，即使没人跑分析。
- **cadence 仍由 `NEWS_INTEL_AUTO_FETCH_MIN_INTERVAL_SECONDS`（20 分钟）控制** —— 不新增第二套频率概念。
- **分析与循环共用同一个冷却** → 天然去重。谁先到谁抓，另一个被冷却跳过。**这正是想要的。**

**不要用 `force=True`。** `refresh_auto_sources(force=True)` 会绕过冷却，导致循环和分析各抓一次。让冷却工作。

### 3.2 两个开关，各管一件事

| 开关 | 管什么 | 代码默认 |
|---|---|---|
| `NEWS_INTEL_AUTO_FETCH_ENABLED`（已存在）| **允不允许**自动抓取 | `False` |
| `NEWS_INTEL_FETCH_LOOP_ENABLED`（新增）| **要不要**用后台循环驱动它，而不依赖分析 | `False` |
| `NEWS_INTEL_FETCH_LOOP_TICK_SECONDS`（新增）| tick 间隔 | `300` |

**两个都默认 `False`** 的理由：
1. 与已有的 `news_intel_auto_fetch_enabled` 默认值一致（那本来就是 opt-in 的网络行为）。
2. **43 个测试文件用 `TestClient`，会触发 lifespan。** 默认开会让测试真的发网络请求 —— 测试变慢、变脆、依赖外网。

循环内部调用 `refresh_auto_sources()`，**后者自己会检查第一个开关**，所以不需要在循环里重复判断。

### 3.3 代码形状（照抄旁边的先例）

`api/app.py:212` 已有一个结构完全相同的后台任务（`_schedule_stock_index_background_refresh`），连 shutdown 处理都写好了。照抄：

```python
# api/app.py —— 与 _schedule_stock_index_background_refresh 同形
def _schedule_intelligence_fetch_loop(app: FastAPI) -> None:
    if not getattr(get_config(), "news_intel_fetch_loop_enabled", False):
        return
    task = getattr(app.state, "intelligence_fetch_loop_task", None)
    if task is not None and not task.done():
        return
    app.state.intelligence_fetch_loop_task = asyncio.create_task(
        _run_intelligence_fetch_loop()
    )

async def _run_intelligence_fetch_loop() -> None:
    interval = max(30, int(getattr(get_config(), "news_intel_fetch_loop_tick_seconds", 300)))
    while True:
        await asyncio.sleep(interval)
        try:
            # refresh_auto_sources 是阻塞的（HTTP 抓取），必须丢到线程里，
            # 否则会卡住整个事件循环 —— API 全部无响应。
            await asyncio.to_thread(
                lambda: IntelligenceService().refresh_auto_sources()
            )
        except asyncio.CancelledError:
            raise
        except Exception:
            # 单次失败不能让循环死掉 —— 下一 tick 继续。
            logger.exception("Intelligence fetch loop tick failed")
```

挂载与收尾（lifespan 内）：

```python
    _schedule_stock_index_background_refresh(app, "startup")
    _schedule_intelligence_fetch_loop(app)          # ← 新增，在 yield 之前
    ...
    try:
        yield
    finally:
        # ...已有的 stock_index_refresh_task 收尾...
        fetch_loop = getattr(app.state, "intelligence_fetch_loop_task", None)   # ← 新增
        if fetch_loop is not None and not fetch_loop.done():
            fetch_loop.cancel()
            with suppress(asyncio.CancelledError):
                await fetch_loop
```

### 3.4 三个必须做对的技术点

| 点 | 为什么 |
|---|---|
| **`asyncio.to_thread`** | `refresh_auto_sources()` 同步阻塞（HTTP）。直接 `await` 会**卡死整个 FastAPI 事件循环**，所有 API 无响应。 |
| **捕获 `Exception` 但不吞 `CancelledError`** | 抓取失败（某个源挂了、网络断了）不能让循环永久死掉；但必须让 `CancelledError` 穿透，否则 shutdown 时取消不掉。 |
| **首次 tick 前不立即抓** | 循环第一件事是 `sleep`。启动瞬间就发网络请求会拖慢冷启动，而且紧接着的第一次分析也会抓 —— 重复。 |

## 四、风险与边界

| 风险 | 处理 |
|---|---|
| 事件循环被阻塞 | `asyncio.to_thread`（见上）|
| 测试发真实网络请求 | 默认关闭；测试里显式断言"关闭时不创建任务" |
| 多进程重复抓取 | 每个 worker 各有一个循环 → 会重复抓。DSA 目前单进程（`webui.py`），**若将来上多 worker，需要用 DB 或文件锁**。记为已知限制。 |
| 抓取比上游缓存还快 | 无害，只是拿到同一份数据。tick 默认 300s > RSSHub 缓存 5min。 |
| 循环与分析并发 | 已有 `_auto_fetch_condition` 锁处理，且返回上一次结果。 |
| 单次 tick 超过 tick 间隔 | 循环体是"睡 → 抓"，抓取耗时长会自然推迟下一次。**不会堆积**（不是固定周期调度）。 |

## 五、验收标准

改完后必须能证明：

1. **默认行为不变**：两个开关都关时，启动日志无抓取、`app.state.intelligence_fetch_loop_task` 不存在。**43 个 TestClient 测试全部仍通过且不发网络请求。**
2. **开启后确实周期性抓取**：开两个开关、tick 设成 30 秒、冷却设成 60 秒，观察**至少两次**抓取发生，且间隔符合冷却（不是 tick）。
3. **冷却真的在去重**：循环抓过一次后，立刻触发一次分析 —— 分析的抓取应被冷却跳过（返回 `skipped: cooldown`），日志可证。
4. **不影响 API 响应**：在抓取进行中打 `/health` 和任意 API，**响应时间不劣化**（证明没有阻塞事件循环）。
5. **shutdown 干净**：停止服务后循环任务被取消，进程正常退出，无 "Task was destroyed but it is pending" 警告。
6. **单次失败不致命**：人为让一个源报错，确认循环在下一 tick 继续运行。

## 六、需要你决定的

**这两个开关的默认值。**

我的建议是**保持代码默认 `False`，在你这套部署的 `.env` 里显式打开**：

- 代码默认 `False` 是诚实的：后台网络循环不该被默默启动，而且能保住 43 个测试不发外网请求。
- 但**这是"部署偏好"，不是"本地绕过"** —— 它会让所有 clone 这个仓库的人默认也拿到手动行为。如果你希望"开箱即用就能自动更新资讯"，那就把代码默认改成 `True`，代价是需要给测试加环境隔离。

**我倾向前者**（默认关 + 部署开），因为它不制造意外行为。你选哪个我就按哪个做。

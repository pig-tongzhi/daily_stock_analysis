# 架构设计：从「能跑」到「可信」

> 本文是决策文档，不是提案清单。每条判断都附实测证据；每个方案都写明取舍与被否决的选项。

## 第一部分 · 诊断

三个独立的深挖各完成一份取证。**结论：这不是三个 bug，是三条同时断裂的链。**

### 断裂线 1 · 判断不可验证

**实测**：手工调用 `POST /api/v1/decision-signals/outcomes/run`，60ms 写入 19 行，但**全部 `unable`**：

```
non_directional_action    18
missing_anchor_price       1
```

**因果链**：

```
分析模型给「观望」（18/19）
   ↓  normalize_decision_action("观望") → action="watch"
   ↓  _direction_for_action("watch") → None
   ↓  non_directional_action
   ↓  且该原因【不可重试】→ 18 行永久死路，永远不自愈
```

**为什么给「观望」**：`LEGACY_DEFAULT_SYSTEM_PROMPT`（`analyzer.py:1949`）里有**四层叠加**的中性偏好，且是**刻意的风控设计**：

| 位置 | 内容 |
|---|---|
| `analyzer.py:1966` | `operation_advice` 枚举里就有"观望" |
| `decision_scale.py:39` | `- 40-59：观望，action=watch` |
| `defaults.py:34` | `乖离率 > 5%：严禁追高！直接判定为"观望"` |
| `analyzer.py:2129` | `资金流不明确时，优先输出"持有/震荡/观望"等中性建议` |

**最后一条字面命中**：`raw_result` 里 `capital_flow_status: "资金流数据缺失"`，`decision_score_calibration: null` —— 44-55 的分数和"观望"是**模型的原始输出**，不是代码钳制。

**同时发现一个能力倒挂**：

| | legacy 路径 | DecisionSignal 路径 |
|---|---|---|
| flat 分支 | ✅ `_classify_outcome` 末尾有 | ❌ `_classify_signal_outcome` 末尾是 `return None, None` |
| "观望"→方向 | ✅ `infer_direction_expected("观望") = "flat"` | ❌ 归一化后丢失 |
| 文档 | ✅ `docs/full-guide.md:1607` 写明 `观望 → flat → 价格在中性带内` | — |

**实测三个收益值喂给两个分类器**：

```
收益 +1.0%   legacy=('win', True)    DecisionSignal=(None, None)
收益 +3.0%   legacy=('loss', False)  DecisionSignal=(None, None)
收益 -1.0%   legacy=('win', True)    DecisionSignal=(None, None)
```

> **新的、更复杂的验证路径，能力弱于它正在替代的旧路径。** 重写时丢了一支。

### 断裂线 2 · 行情数据断供

**实测**：`stock_daily` 516 行 / 10 个代码 / 全部停在 **2026-09-30**。

**前提修正**：不是我先前说的"断了 10 天"。交易日历显示 `2026-09-28, 09-29, 09-30, 10-08, 10-09, 10-12` 是交易日；**10-01~10-07 是国庆假期，10-10 是周六**。**真正缺的是 10-08 和 10-09 两个交易日。**

**根因是"机件在但从未被触发"**：

```
10-02 分析：目标日期解析 → 假期前最后交易日 = 09-30 → 写入 42 行/代码
10-05 分析：仍在假期 → 又解析到 09-30 → 断点续传命中 → 跳过获取
            （日志实证：7 个代码全部记录 "2026-09-30 数据已存在，跳过获取"）
SCHEDULE_ENABLED=false → 之后没有任何每日拉取
```

**两个真缺陷**：

**缺陷 A · 抓到的数据被扔掉**
```
今天 12:56:43  analyze_trend 工具成功抓到 600559 的 79 行（范围到 2026-10-10）
              但它【不落库】—— 工具声明 side_effects 里没有 db_write
              → 表仍停在 09-30
```

**缺陷 B · `force_refresh` 在 API 路径被静默丢弃**
```
api/schemas/analysis.py:52   声明了 force_refresh
task_queue.py:817            转发了它
analysis_service.py:81       接收了它
analysis_service.py:162      调用 process_single_stock(...) 时【没传】
pipeline.py:3295             process_single_stock 根本没这个参数
→ POST /analyze {"force_refresh": true} 无法绕过断点续传
```

**最隐蔽的后果**：

```python
# storage.py:3489 get_analysis_context
# 显式注释（:3502-3505）：忽略 target_date
get_latest_data(code, days=2)
```

> **数据陈旧时，LLM 被告知「2026-09-30 就是今天」。**

8 个消费方受影响：验证闭环、skill 闭环、回测、组合估值、分析上下文、K线工具、选股、环境诊断。

### 交叉结论 · 四个结构性问题

**A · 新旧路径能力倒挂**
`_classify_outcome`（旧）有 flat 分支，`_classify_signal_outcome`（新）没有。**重写丢了能力。**

**B · 代码身份不统一**
```
stock_daily 存       000063.SZ
decision_signals 存  000063        → 查不到
588200                               → stock_daily 里完全没有
stock_daily 内部     000063.SZ 与 002043 混用
canonical_id 已引入（storage.py:138-142），但读取路径仍查 code
```

**C · 基础设施过剩、数据饥饿**
```

7 张验证/回测表         已建
memory 反馈回路         已实现（命中率 → confidence_adjustment）
base_agent.py:280       真的会读它

→ 全部拿不到数据，全是惰性的
```

**D · "今天"没有单一来源**
每处各自解析：`_resolve_resume_target_date`、`get_effective_trading_date`、`_anchor_date`、`get_analysis_context`（忽略）、`load_history_df`（用 `date.today()`）。**五个地方，五种"今天"。**

## 第二部分 · 方向

### 核心判断

> **这个项目缺的不是功能，是三个「单一事实来源」。**
> 而它已有的东西（验证引擎、反馈回路、19 个工具）**全都在等这三样**。

| 需要统一的 | 现在 | 应该 |
|---|---|---|
| **"今天"** | 5 处各自解析，其中 1 处直接忽略 | 交易日历是唯一权威 |
| **"这只股票"** | `000063` / `000063.SZ` / 缺失三种形态 | `canonical_id` 是唯一键 |
| **"我的判断"** | 一句话，无法验证 | 带期限、可证伪的契约 |

### 为什么不是先做别的

| 候选方向 | 为什么不是第一优先 |
|---|---|
| 给选股加资讯因子 | **交集为 0**。加因子只是多一段噪声进 prompt，还会挤掉候选详情（负收益） |
| 扩充资讯源 | 采集不是瓶颈。**池里有 302 条，问题是它们不关于选股选出的股票** |
| 原始数据落盘 | 仍然必要（可演化性），但**它不能证明任何结论**，闭环才能 |
| 改善 UI | 不解决"从不学习" |

### 最高价值的一步

**修好并自动化闭环。** 理由：

1. **管道已通**（实测 19 行一次写入，60ms），改造成本最低
2. **表已建、服务已写、API 已在、问股已在读** —— 缺的只是让判断可验证
3. 它把"产出结论"变成"**可证伪的预测**" —— 这是项目与玩具的分界
4. 它立刻产出你**真正想要却拿不到**的东西：**我的判断到底准不准**
5. 它是后续所有校准的依据 —— 没有它，加工层权重只能拍脑袋

## 第三部分 · 架构

### 分层的实际含义

```
┌──────────────────────────────────────────────────────────────────┐
│ L0  采集   独立节奏，不管谁用                                       │
│     RSSHub · NewsNow · 搜索 · AkShare · 公告 · 行情                │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│ L1  资产   ★ 现在最缺                                              │
│     raw_documents    原始响应，不可变，抓什么存什么                 │
│     news_items       规范化条目（去重/时间/来源/正文）              │
│     stock_daily      行情（★已有，需修好供给）                     │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│ L2  加工                                                          │
│     entity_linking   资讯 → 股票（canonical_id）                   │
│     event_tags       事件分类                                      │
│     impact_scores    方向 + 强度 + 时效                            │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│ L3  能力   四者共享 L1 + L2                                        │
│     选股 · 问股 · 推测 · 股票信息                                   │
└────────────────────────────┬─────────────────────────────────────┘
                             ↓
┌──────────────────────────────────────────────────────────────────┐
│ L4  闭环   ★ 代码全在，两端断                                      │
│     判断 → 到期验证 → 命中率 → confidence_adjustment → 反哺         │
└──────────────────────────────────────────────────────────────────┘
```

### 但真正重要的是四条「契约」

分层是结构，**契约才是约束**。四条契约贯穿所有层：

#### 契约 1 · 时间

**唯一权威**：`src/core/trading_calendar.py`

**规则**：
- 任何"这一天有交易吗"的问题**只能问它**
- 任何"锚点日期"必须先经 `resolve_historical_daily_bar_date` 归一
- **禁止**任何地方直接用 `date.today()` 或 `session_date` 原文
- `get_analysis_context` 必须接受并使用 `target_date`

**验收**：全仓 grep `date.today()` 只剩交易日历内部使用。

#### 契约 2 · 身份

**唯一权威**：`canonical_id`（`storage.py:138-142` 已引入）

**规则**：
- 写入时生成，读取时**统一查它**
- 所有跨表 join 用它，不用 `code`
- 输入侧（`000063` / `000063.SZ` / `sz000063`）经一个解析器归一

**验收**：`get_daily_on_date(code='000063')` 能查到 `000063.SZ` 的行。

#### 契约 3 · 判断

**规则**：**每个进入 `decision_signals` 的判断必须可验证。**

具体：
- `action` 必须映射到一个可评分的方向：`up` / `not_down` / `not_up` / `flat`
- `watch` 必须映射到 `flat`（**语义已存在，只是新路径没接**）
- 锚点日期必须是交易日
- **`unable` 的原因必须全部可重试**（现在的 `non_directional_action` 不可重试，是数据模型的错）

**验收**：19 个历史信号重跑，`unable` 比例从 100% 降到可解释的水平。

#### 契约 4 · 证据

**规则**：任何结论可追溯到原始数据。

具体：
- `raw_payload` 存**真实原始响应**，不是来源标签
- 判断记录它依据的资讯 ID
- 验证结果记录它依据的行情行

**验收**：任取一条历史判断，能还原出当时的原始输入。

### 4.1 断裂线 1 的修法（判断可验证）

**改动 1 · 补回 flat 分支**（2 处，共 5 行）

```python

@staticmethod

    if action in {"buy", "add"}:      return "up"
    if action == "hold":              return "not_down"
    if action in {"reduce","sell","avoid"}: return "not_up"
    if action == "watch":             return "flat"        # ← 新增
    return None
```

```python
# src/core/backtest_engine.py:643-675  _classify_signal_outcome 末尾
if direction_expected == "flat":                            # ← 新增
    if abs(r) <= band: return "hit", True
    return "miss", False
return None, None
```

**依据**：`infer_direction_expected("观望") = "flat"` 已存在；`_classify_outcome` 已有该分支；`docs/full-guide.md:1607` 已文档化。**这是恢复语义，不是发明语义。**

**改动 2 · 锚点日期走交易日历**

**改动 3 · `non_directional_action` 改为可重试**

理由：判断语义可能随版本变化，**死路会永久污染历史**。改为可重试后，`engine_version` 变化时自动重算。

**改动 4 · `neutral_band_pct` 接配置**

```python

# backtest_neutral_band_pct 已存在于 config.py:1196，backtest_service.py:76 已在用

**改动 5 · 措辞对齐**（可选，但收益明确）

`震荡观望` 已经映射到 `not_down`（可评分），而 `观望` 映射到 `flat`。两者都变可评分后，这一条不再是必需，但**统一措辞能减少歧义**。

**被否决的选项**：
- ❌ **改提示词逼模型给方向** —— 会把系统变成掷硬币的机器，且**破坏刻意的风控设计**
- ❌ **用 `decision_profile=aggressive`** —— 实测无效：`extractor.py:108/150` 硬编码 `"balanced"`，`_apply_profile_bias` 完全忽略 profile
- ❌ **只补资金流数据** —— `stabilize_decision_with_structure` **只会降级，从不升级**，必要但不充分

### 4.3 断裂线 3 的修法（资讯与选股）

**先明确：这一步不该先做。** 但设计要给出来。

**改动 11 · 资讯覆盖策略（这是根问题）**

现状：6 个手工配置的 symbol 源，覆盖自选股。选股选的是别处的股票。

三个选项：

| 选项 | 做法 | 取舍 |
|---|---|---|
| **A. 按需建源** | 选股产出候选后，为 top-K 动态创建 symbol 源，下一轮生效 | **有延迟**（第一轮无资讯），但覆盖精准、成本可控 |
| **B. 全市场预建** | 为 5,565 只各建一个源 | 源数量爆炸，RSSHub 压力大，绝大部分永不命中 |
| **C. 只做事件型资讯** | 不追个股，改抓"影响面广"的事件（政策/行业/龙头），用实体链接映射到候选 | 需要实体链接层（L2），但**覆盖面天然最广** |

**推荐 A + C 组合**：
- **C 打底** —— 行业/政策/宏观事件天然影响大量股票，用实体链接映射
- **A 补充** —— 对反复入选的候选按需建源，把精准度补上

**改动 12 · 资讯必须能进数值层**

现在资讯只进 prompt。要让它真正影响排序，必须：

df = compute_screen_scores(df, screening)

```

**关键**：必须在 `compute_screen_scores` **之前** join。现在 `context.py:422-424` 会丢弃不在候选池里的行，实测注入 0 字符。

**改动 13 · 缓存指纹**

### 4.4 贯穿性改动

## 第七部分 · 我认为最容易被忽略的三个陷阱

**陷阱 1 · "修好了"的自我欺骗**
实测已经两次打脸：我先前说"断了 10 天"，实际是 2 个交易日；我说"修了 HK10000"，实际只修了切换判定。**每个结论都必须有可复现的命令。**

**陷阱 2 · 新旧路径并存**
这次的 flat 分支倒挂就是典型。**每次重写都要问：旧路径有什么能力是新的没有的？**

**陷阱 3 · 沉默的降级**
`no_json_found`（截断）、`non_directional_action`（无方向）、`data_source='AkshareFetcher'` 但数据没落库 —— **系统在悄悄失败，而日志说它成功了**。每个降级点都必须显式、可计数、可告警。

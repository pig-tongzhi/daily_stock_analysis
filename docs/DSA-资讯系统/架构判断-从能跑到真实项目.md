# 架构判断：从"能跑"到"真实项目"

## 一、诊断：缺的不是功能，是两样东西

系统现在有 10 个选股策略、能问股、能分析、能复盘、23 个资讯源。**功能不缺。**

缺的是两样结构性东西：

### 缺口 1：资讯是**消耗品**，不是**资产**

```
抓取 → 解析 → 塞进 prompt → 用完即弃
                ↑
        原始数据在这里就丢了
```

证据：

| 现象 | 后果 |
|---|---|
| `raw_payload` 302 条全是 `{"source": "..."}` | 解析规则一旦有 bug，**原始数据永久丢失，无法重放** |
| 选股的 AkShare 抓取**完全不落盘** | 同一个候选每跑一次选股就重复请求一次网络 |
| 保留期按 `fetched_at`，而每次抓取都刷新它 | 保留期形同虚设，旧文章永不淘汰（80/302 条已超 30 天）|
| 搜索的 `news_intel` 只有 10 行、独立一张表 | 三个资讯存放处互不相通 |

**一个不能回溯的数据集，无法演化。** 这就是它现在像"脚本集合"而不像"项目"的根本原因。

### 缺口 2：判断**没有闭环** —— 而且不是"没建"，是**两端都断了**

**已实测。** 闭环的每一段代码都存在，我手工跑了一次到期验证：

```
POST /api/v1/decision-signals/outcomes/run  {"force": true}
→ HTTP 200, evaluated 19, created 19, skipped 0
→ decision_signal_outcomes: 0 行 → 19 行        ← 管道是通的
```

**但 19 条全部是 `unable`：**

```
unable_reason
  non_directional_action    18     ← 判断没有方向
  missing_anchor_price       1
```

**根因是一条完整的因果链：**

```
① 分析模型倾向给「观望」—— 最安全的答案
        ↓
② action=watch  观望 占 18/19（唯一一个 buy 是 600519）
        ↓
③ 验证器判定 non_directional_action —— 无方向就无法判对错
        ↓
④ 闭环永远闭不上
        ↓
⑤ 系统永远学不到东西，无法通过反馈改进
```

**为什么模型倾向给"观望"**：早先盘个股预测时发现，**7 只不同的股票给了 7 个一模一样的「观望 + 震荡」**。观望不会被证伪得太难看，但**不携带任何可验证的信息**。

**第二个独立的断点**：

```
stock_daily 最新数据 = 2026-09-30
今天              = 2026-10-10
→ 行情断了 10 天。就算判断有方向，1d/3d/5d 的收益也算不出来。
```

**这是两个独立故障，必须都修**：光让模型给出方向，行情跟不上仍然算不出来；光补行情，判断无方向仍然是 `unable`。

**这正是"像脚本集合而不像项目"的根本原因**：它产出结论，但**从不学习**。

## 二、四个能力现在是**四座孤岛**

```
选股  ──→ 自己的路径：AkShare 现拉(默认关) + 本地池(默认关)
问股  ──→ 自己的路径：Bocha 搜索 API（未配，news_intel 只有 10 行）
推测  ──→ 只记录，不验证（outcomes 表是空的）
行情  ──→ 各自现拉，不共享
```

**四者之间没有共享的数据层。** 每条路径各抓各的、各存各的、各丢各的。

## 三、目标架构

```
┌────────────────────────────────────────────────────────────────────────┐
│ L0  采集层  Acquisition                          独立节奏，不管谁用     │
│     RSSHub · NewsNow · 搜索 · AkShare · 公告 · 行情                     │
│     ↓ 统一写入，保留原始响应                                            │
└────────────────────────────────────────────────────────────────────────┘
                                  ↓
┌────────────────────────────────────────────────────────────────────────┐
│ L1  资产层  Data Assets                        ★ 现在最缺的一层        │
│                                                                        │
│     raw_documents    原始文档，不可变。抓什么存什么，永不丢。            │
│     news_items       规范化条目：去重、时间、来源、正文                  │
│     stock_snapshots  行情/技术/筹码快照（可复用的时点数据）              │
└────────────────────────────────────────────────────────────────────────┘
                                  ↓
┌────────────────────────────────────────────────────────────────────────┐
│ L2  加工层  Enrichment                                                 │
│                                                                        │
│     entity_linking   资讯 → 股票/行业/概念 实体                        │
│     event_tags       事件分类（业绩/监管/合同/减持…）                   │
│     impact_scores    影响方向 + 强度 + 时效衰减                        │
│                                                                        │
│     ★ 产出的是【可计算的特征】，不只是一段塞进 prompt 的文本             │
└────────────────────────────────────────────────────────────────────────┘
                                  ↓
┌────────────────────────────────────────────────────────────────────────┐
│ L3  能力层  Capabilities                       四者共享 L1 + L2        │
│                                                                        │
│     选股        候选 → 特征 → 排序（特征来自 L2，不再现拉）              │
│     问股        问题 → 检索资产层 → 回答（可引用来源，不只靠搜索）        │
│     推测        判断 → 记录 → 到期验证 → 偏差 → 校准  ★闭环            │
│     股票信息    一只股票的全部已知：行情+技术+资讯+历史判断+验证结果     │
└────────────────────────────────────────────────────────────────────────┘
                                  ↓
┌────────────────────────────────────────────────────────────────────────┐
│ L4  闭环层  Feedback                                                   │
│                                                                        │
│     判断入库 → 到期自动验证 → 命中率/偏差分析 → 反过来校准 L2 的权重     │
└────────────────────────────────────────────────────────────────────────┘
```

## 四、"用资讯去推测"到底是什么 —— 这是最需要澄清的

**含糊的说法**："用资讯预测股票走势。"

**可做、可验收的说法**：

> 从资讯中形成**带期限、可证伪**的预期，到期自动比对实际结果，并累积偏差统计。

具体形态：

```
① 形成预期      "600559 老白干酒：现金流改善 + 机构上调评级
                 → 预期 5 个交易日内相对沪深300 取得正超额"
                 （附：依据的资讯条目 ID、置信度、形成时间）

② 记录          decision_signals（已有表，已在用）

③ 到期验证      decision_signal_outcomes（已有表，★从未写入）
                 5 个交易日后自动取实际涨跌，填 outcome / direction_correct

④ 校准          统计：哪类资讯→预期 的命中率高？
                 哪类事件标签是噪声？
                 → 反过来调 L2 的 impact_scores 权重
```

**关键：③ 是当前唯一缺失的环节，而表已经建好了。**

**证据它可行**：你几天前问"今天的大盘符合我们的判断预期吗"，我手工做了 ①→③（对比 10/5 判断 vs 10/8 实际，判定条件式预警命中）。**那个流程完全可以自动化。**

## 五、关键设计决策（含取舍）

### 决策 1：原始文档必须落盘，且不可变

**理由**：这是"能不能演化"的分水岭。现在解析完就丢原始数据，等于**锁死了未来所有解析改进**。

**取舍**：存储成本上升。但资讯是文本，量级很小（当前 302 条全库 5.4 MB）。**用 SQLite 存原始 JSON/HTML 完全够用。**

### 决策 2：从「文本注入」升级到「结构化信号」

**现在**：资讯被拼成一段文字塞进 prompt。
**目标**：资讯先变成特征（事件类型、影响方向、强度、时效），再决定怎么用。

**理由**："推测"要求可计算、可回归、可校准。一段文字没法做偏差统计。

**取舍**：加工层有成本（每篇文章要做实体识别+事件分类）。**分两层做：规则优先（关键词/正则），LLM 只处理规则拿不准的。**

### 决策 3：四个能力共享同一层，但**不强制统一**

**理由**：强行统一四种不同需求会做出一个谁都不好用的抽象。
**做法**：统一的是**数据访问**（L1/L2 一个查询接口），不是业务逻辑。

### 决策 4：采集独立于消费

**理由**：资讯的更新节奏（分钟级）与分析的节奏（小时/天级）差两个数量级。绑在一起必然有一方不合适。
**做法**：就是 P0 那个循环。

## 六、实施顺序（每阶段独立可验收）

**原则：每一步都能单独上线、单独验证，不做大爆炸式重构。**

### 阶段 0：地基（改动小，收益立竿见影）

| 做什么 | 验收 |
|---|---|
| `raw_payload` 存真实原始响应 | 抓一次，能从库里还原出原始的 RSS/JSON |
| 保留期改按 `published_at`（空则退回 `fetched_at`）| 30 天前的条目真的被清理 |
| 去重键去掉 `source_id` | 同一条新闻不再存两份 |
| 修 2 个源的 `published_at` 解析 | 302 条里 0 条缺时间 |

**这一阶段不改变任何现有行为**，只是让已有数据变得可靠。

### 阶段 1：采集独立（= P0）

独立循环，20 分钟 tick，复用现有冷却。**资讯开始自己更新，不再依附分析。**

### 阶段 2：合并资讯存放处

把 `news_intel`、AkShare 现拉的结果**都写进同一层**，一个查询接口。**选股不再现拉。**

### 阶段 3：实体链接 + 事件标签

资讯 → 股票。**这是"资讯能影响选股"的前提**：现在选股从 5500 只里挑，而池里只有 6 只自选股的 symbol 源，命中率接近 0。

### 阶段 4：修好并自动化闭环（**我认为这是最有价值的一步**）

**注意：不是"建设"，是"修复 + 接通"。** 代码全在，实测能跑，但两端断了（见缺口 2）。

| 做什么 | 验收 |
|---|---|
| **修数据端**：让 `stock_daily` 每日更新（现在停在 2026-09-30）| 到期验证能真的算出 1d/3d/5d 收益 |
| **修判断端**：让分析产出**有方向、带期限**的判断 | `non_directional_action` 比例从 95% 降下来 |
| **接调度**：把 `outcomes/run` 放进调度器（现在只能手动调）| 无需人工，每天自动回填 |
| **出统计**：基于 `outcomes/stats` 给出命中率 | 能回答"过去 30 天方向命中率多少" |

**为什么它最有价值**：
- 管道已通（实测 19 条一次写入），**改造成本最低**
- 它把"产出结论"变成"**可证伪的预测**"，这是项目与玩具的分界线
- 它立刻产出你**真正想要却拿不到**的东西：**我的判断到底准不准**
- 它是后续所有校准的依据 —— 没有它，加工层的权重只能拍脑袋

**难点在"判断端"**：模型倾向给观望，因为观望最安全。要让它产出可验证的判断，得改提示词并**用命中率来约束它** —— 这正是闭环存在的意义：**让"说废话"付出代价。**

### 阶段 5：推测层

在闭环基础上，从资讯生成**带期限的可证伪预期**，自动跟踪。

---

## 七、如果只做一件事

**做阶段 4（闭环验证）。**

理由：
- **表已经建好了**（`decision_signal_outcomes`），19 条信号在等着被验证
- 它把"记录"变成"可证伪的预测"，这是**项目与玩具的分界线**
- 它立刻产出**你真正想要却拿不到的东西**：我的判断到底准不准
- 它是后续所有校准的依据 —— 没有它，加工层的权重只能拍脑袋

**而且它有现成的验收方式**：拿你前几天那次大盘判断做回归测试。

---

## 八、我的建议顺序

```
阶段 0（地基）  → 阶段 4（闭环）  → 阶段 1（采集独立）  → 阶段 2（合并）  → 阶段 3（实体）  → 阶段 5（推测）
   ↑                  ↑
 让数据可靠        让判断可验证
```

**先地基再闭环**：如果原始数据在丢，验证出来的结论也不可信。
**闭环优先于采集**：采集是"更多数据"，闭环是"数据有没有用"。**先知道准不准，再决定要不要更多。**
